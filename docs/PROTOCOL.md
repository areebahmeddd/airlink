# Protocol

What a relay node must do to join an Airhop, bitchat-ios and bitchat-android mesh without changing how the mesh behaves: each rule, where it is implemented and the test that covers it. Airhop's `docs/spec/PROTOCOLS.md` is the specification; bitchat-ios is the reference where the two clients differ.

Every rule below has a host test (`test/host`, under ASan and UBSan) unless its row names a device or hardware check; the hardware scenarios in [TESTING.md](TESTING.md) confirm them on real boards and phones.

**Signatures checked before relaying.** Most types are forwarded without a signature check, but bitchat-ios verifies `LEAVE`, `FILE_TRANSFER`, `BOARD_POST` (its inner author signature) and live voice before relaying them, and Airhop's PROTOCOLS section 3.6 adds live video. The node does too, so a forged leave or board post dies at the first hop, as it would at a phone. The checks are budgeted (`AH_VERIFY_PER_SECOND`), and a live stream's key is checked once per stream and link: its sender and stream ID travel in clear, so a packet riding them over another link is checked as a new stream. On the link it verified over, a later packet of the stream is relayed on its shape alone, so a copy with a broken signature that reaches the node first is relayed and the genuine one dropped as its duplicate; the phones beyond drop that copy, and lose one frame, which an attacker able to race the stream could more cheaply take by jamming. Each check is charged to the link its packet came over, and each open link is held an even share of each second's budget, at least one check (and only one while it has been quiet for two seconds), so a flood of forged packets on one link spends only that link's share and what no link is held: the other links' checks still run. A failed check is not remembered, since a forgery costs its sender nothing to vary. The node's own checks (announces, the messages it keeps, requests, deposits) leave a quarter of their link's share, and of the budget, to the checks before a relay decision, and a `REQUEST_SYNC` past its rate is refused before its signature is checked. A pre-relay check, a sync reply's or a deposit's put off for lack of budget is neither a pass nor a failure: nothing is recorded against the packet, so its next copy is checked again. A packet already relayed is a duplicate when it comes again, so one whose own check was put off is relayed but not acted on, and is kept only once a sync reply brings it: a reply is never relayed, so one carrying a packet the node relayed but never kept is checked and kept then, while the packet's ID stays recorded. Tests: `test_forged_board_posts_and_live_packets_never_cross`, `test_a_sync_burst_past_the_verify_budget_is_offered_again`, `test_a_flood_on_one_link_never_spends_another_link_s_checks`, `test_a_budget_smaller_than_the_links_still_holds_one_check_each`, `test_a_sync_request_past_the_rate_costs_no_signature_check`, `test_a_message_relayed_but_not_kept_is_kept_from_a_sync_reply`.

## Privacy: No Phone Adjacency on the Air

The node never emits TLV `0x04` (direct neighbors), so it never lists the phones beside it, and so it plans no routes either; it follows routes others plan, as Airhop does. It keeps no topology table. Test: `test_announce_round_trip_with_relay_tlvs` checks the node's own announce has no `0x04`.
